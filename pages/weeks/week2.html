1. Why Pandas? The Data Science Workhorse

Pandas has two core data structures: Series (1D — like a single column) and DataFrame (2D — like a full spreadsheet).

Almost all ML workflows start with loading a DataFrame from a CSV file.

2. Series — A Labeled 1D Array

A Pandas Series is a one-dimensional array-like object that contains a sequence of values associated with a labeling array, called its index.

python — series_basics.py 
import pandas as pd

# Create a Series from a list — auto-indexed 0,1,2...
scores = pd.Series([85, 92, 78, 95, 88])
print(scores)
# 0    85
# 1    92  (left = index, right = value)
# 2    78
# dtype: int64

# Custom index (like a labeled Excel column)
student_scores = pd.Series(
    [85, 92, 78],
    index=["Rahul", "Priya", "Arjun"]
)
print(student_scores["Priya"])  # 92
print(student_scores.mean())    # 85.0
print(student_scores.max())     # 92

A DataFrame represents a tabular, spreadsheet-like data structure containing an ordered collection of columns, each of which can be a different value type.

4. Selecting Data — iloc, loc, Boolean Indexing

Pandas offers optimized label-based selection using loc , position-based selection using iloc , and conditional filtering using Boolean masks.

python — selection.py 
# --- Column selection ---
print(df["name"])               # single column → Series
print(df[["name", "salary"]])  # multiple columns → DataFrame

# --- iloc: Integer-based (position) ---
print(df.iloc[0])         # row at position 0 (first row)
print(df.iloc[0, 2])      # row 0, column 2 → "Mumbai"
print(df.iloc[1:3])       # rows 1 and 2 (slice)

# --- loc: Label-based (use column name) ---
print(df.loc[0, "name"])  # row 0, column "name" → "Rahul"
print(df.loc[:, "salary"]) # all rows, salary column

# --- Boolean indexing (most used in ML!) ---
high_earners = df[df["salary"] > 55000]
mumbai_people = df[df["city"] == "Mumbai"]
young_rich = df[(df["age"] < 24) & (df["salary"] > 50000)]

8. Binning Continuous Data — cut() and qcut()

import pandas as pd

# cut() — fixed bin edges (YOU define the boundaries)
df["age_group"] = pd.cut(
    df["age"],
    bins=[0, 18, 35, 60, 100],
    labels=["child", "young", "middle", "senior"]
)

# qcut() — quantile-based cut (equal FREQUENCY in each bin)
df["salary_quartile"] = pd.qcut(df["salary"], q=4,
    labels=["Q1", "Q2", "Q3", "Q4"])

# When to use which?
# cut()  → you know domain boundaries (0-18 is minor, etc.)
# qcut() → you want equal population in each bucket
cut() and qcut() are core feature engineering tools.

Age groups, salary bands, and risk tiers are all created this way before feeding data into ML models.

9. Slicing Caution: SettingWithCopyWarning & .copy()

When you slice a subset of a DataFrame (e.g. subset = df[df["salary"] > 55000] ) and then try to modify it (e.g. subset["bonus"] = 100 ), Pandas will frequently throw a SettingWithCopyWarning .

This happens because Pandas is unsure whether your slice is a View (points to the original data) or a Copy (a separate object in memory).

Modifying a view modifies the original, while modifying a copy does not.

How to fix it: If you want a completely independent copy to modify safely, explicitly use .copy() :

python — safe_copy.py 
# Safe way to modify a sliced subset without warnings
high_earners = df[df["salary"] > 55000].copy()
high_earners["bonus"] = high_earners["salary"] * 0.1  # Safe! No warning.

# If you WANT to modify the original DataFrame, use .loc:
df.loc[df["salary"] > 55000, "bonus"] = df["salary"] * 0.1  # Safe and direct!

# contact_book.py — Python Review Warm-up
import csv, os

class Contact:
    def __init__(self, name, phone, email, city):
        self.name = name.strip().title()
        self.phone = phone.strip()
        self.email = email.strip().lower()
        self.city = city.strip().title()

    def __str__(self):
        return f"{self.name:<18} | {self.phone:<12} | {self.email:<23} | {self.city}"

    def to_dict(self):
        return {"name":self.name,"phone":self.phone,"email":self.email,"city":self.city}

class ContactBook:
    FIELDS = ["name","phone","email","city"]

    def __init__(self, filename="contacts.csv"):
        self.filename = filename
        self.contacts = []
        self.load()

    def load(self):
        if not os.path.exists(self.filename): return
        try:
            with open(self.filename,"r") as f:
                for row in csv.DictReader(f):
                    self.contacts.append(Contact(row["name"],row["phone"],row["email"],row["city"]))
        except Exception as e:
            print(f"Load error: {e}")

    def save(self):
        with open(self.filename,"w",newline="") as f:
            w = csv.DictWriter(f,fieldnames=self.FIELDS)
            w.writeheader()
            w.writerows([c.to_dict() for c in self.contacts])

    def add(self):
        name = input("Name: ")
        if any(c.name.lower()==name.lower() for c in self.contacts):
            print("Contact already exists!"); return
        self.contacts.append(Contact(name, input("Phone: "), input("Email: "), input("City: ")))
        self.save(); print("✅ Contact added!")

    def search(self):
        q = input("Search (name/city): ").lower()
        results = [c for c in self.contacts if q in c.name.lower() or q in c.city.lower()]
        for c in results: print(c)

    def delete(self):
        name = input("Delete contact name: ")
        for i, c in enumerate(self.contacts):
            if c.name.lower() == name.lower():
                self.contacts.pop(i)
                self.save(); print("✅ Deleted!"); return
        print("Contact not found!")

    def list_all(self):
        if not self.contacts: print("No contacts yet!"); return
        for c in sorted(self.contacts, key=lambda c: c.name): print(c)

def main():
    book = ContactBook()
    menu = {"1":book.add,"2":book.search,"3":book.delete,"4":book.list_all}
    while True:
        print("\n📒 1.Add 2.Search 3.Delete 4.List 5.Exit")
        choice = input("Choice: ").strip()
        if choice == "5": break
        if choice in menu: menu[choice]()

if __name__ == "__main__":
    main()

1. Database & RDBMS Fundamentals

A Database is an organized collection of structured information or data, typically stored electronically in a computer system.

A Relational Database Management System (RDBMS) is a type of database management system (DBMS) that stores data in tables (relations) of rows (tuples) and columns (attributes), and manages data based on the relational model.

Entity Relationships & Junction Tables

Databases model the real world via three primary relationship types:

  • One-to-One (1:1): A row in Table A is linked to exactly one row in Table B. E.g., A user has exactly one user_profile .
  • One-to-Many (1:N): A row in Table A can be linked to multiple rows in Table B. E.g., A department has multiple employees , but each employee belongs to only one department.
  • Many-to-Many (M:N): Multiple rows in Table A can relate to multiple rows in Table B. E.g., students can enroll in multiple courses , and each course has multiple students. This is resolved in databases using a Junction Table (also called Join or Bridge table) that stores pairs of foreign keys.

2. SQL vs. Pandas — The Paradigm Shift

As a data scientist, you already know Pandas.

But Pandas has a limit: it loads the entire dataset into RAM .

If you have a 50GB dataset and 16GB of RAM, Pandas will crash.

SQL (Structured Query Language) solves this.

SQL is declarative (you define what data you want, not how to get it) and operates directly on database files stored on disk, streaming only the necessary results to your computer.

4. Aggregations, GROUP BY & The HAVING Scaffold

Suppose you want to find statistics about departments.

We use Aggregations (like SUM or AVG ) to collapse multiple values into one.

But how do we group them?

sql — group_by_basics.sql 
-- Simple Aggregation (Pandas: df['salary'].mean())
SELECT AVG(salary) AS avg_sal FROM employees;

-- Grouping rows (Pandas: df.groupby('department')['salary'].mean())
SELECT department, AVG(salary) AS avg_sal, COUNT(*) AS headcount
FROM employees
GROUP BY department;

The HAVING Limitation (Where vs Having)

What if you want to filter out departments with an average salary of less than 60,000?

Your first instinct might be to write this:

sql — wrong_where.sql 
-- ❌ THIS WILL FAIL WITH A SYNTAX ERROR!
SELECT department, AVG(salary)
FROM employees
WHERE AVG(salary) > 60000  -- Aggregates not allowed in WHERE
GROUP BY department;

-- ✅ CORRECT: HAVING filters AFTER grouping
SELECT department, AVG(salary) AS avg_sal
FROM employees
GROUP BY department
HAVING AVG(salary) > 60000;

5. JOINs — Combining Tables from First Principles

When data is split across tables (e.g. employees and departments ), we must join them.

Let's understand how a join actually works step-by-step.

Step 1: The Cartesian Product (CROSS JOIN)

If you join two tables without any matching keys, the engine matches every row of Table A with every row of Table B.

If Table A has 100 rows and Table B has 10 rows, the result is 1,000 rows.

This is a Cartesian Product.

sql — cross_join.sql 
SELECT e.name, d.department_name
FROM employees e
CROSS JOIN departments d;  -- Matches everything with everything

Step 2: INNER JOIN (Filtering the Cartesian Product)

To make the join meaningful, we add an ON clause.

This acts like a filter on the Cartesian Product, retaining only rows where keys match (e.g. e.dept_id = d.id ).

sql — inner_join.sql 
SELECT e.name, d.department_name
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;  -- Only matching records kept

Step 3: LEFT JOIN (Handling Dangling Keys)

If an employee has a dept_id of NULL (or a department that doesn't exist), the INNER JOIN will drop that employee row.

We call this a dangling key .

To retain all employees regardless of whether they have a department match, we use a LEFT JOIN .

sql — left_join.sql 
SELECT e.name, d.department_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id;  -- Retains all employees, shows NULL if no match

6. Complete JOIN Family — FULL OUTER, CROSS, SELF

SQL joins combine rows from two or more tables based on a related column, supporting full outer, cross, and self join strategies for relational queries.

sql — all_joins.sql 
-- RIGHT JOIN — all from right table (mirror of LEFT JOIN)
SELECT e.name, d.department_name
FROM employees e RIGHT JOIN departments d ON e.dept_id = d.id;

-- FULL OUTER JOIN — all rows from BOTH, NULLs where no match
SELECT e.name, d.department_name
FROM employees e FULL OUTER JOIN departments d ON e.dept_id = d.id;

-- CROSS JOIN — every combination (m×n rows). Use carefully!
SELECT a.color, b.size FROM colors a CROSS JOIN sizes b;

-- SELF JOIN — join a table to itself (e.g. employee → manager)
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

🧠 Theory & Concepts

1. Subqueries — The "Stuck Query" Problem

Suppose you want to find employees who earn more than the average salary of the entire company.

Your first instinct might be to write this query:

sql — wrong_where_aggregate.sql 
-- ❌ THIS WILL FAIL WITH A SYNTAX ERROR!
SELECT name, salary
FROM employees
WHERE salary > AVG(salary);  -- Aggregates not allowed in WHERE

To solve this, we nest a query inside another query.

The inner query calculates the average first, and its single output value is handed to the outer query for row filtering:

sql — independent_subquery.sql 
-- ✅ Independent Subquery: Runs exactly once first, then filters the outer query
SELECT name, salary
FROM employees
WHERE salary > (
    SELECT AVG(salary) FROM employees
);

-- Subquery with IN (finding employees who work in departments located in Mumbai)
SELECT name 
FROM employees
WHERE dept_id IN (
    SELECT id FROM departments WHERE location = 'Mumbai'
);

Correlated Subqueries — The Performance Bottleneck

Unlike independent subqueries which run once, a Correlated Subquery references columns from the outer query.

The database engine must execute the inner query once for every single row processed by the outer query.

This is physically slow and should be avoided on large datasets unless optimized.

sql — correlated_subquery.sql 
-- Find employees earning more than the average salary of THEIR specific department
SELECT e1.name, e1.salary, e1.dept_id
FROM employees e1
WHERE e1.salary > (
    SELECT AVG(e2.salary)
    FROM employees e2
    WHERE e2.dept_id = e1.dept_id  -- Binds inner query to the current outer row
);

2. CTEs (WITH clause) — Solving the "Spaghetti Query"

If you need to perform multiple levels of aggregations or joins on subqueries, nesting them quickly turns your SQL script into unreadable spaghetti code.

For example:

sql — nested_spaghetti.sql 
-- ❌ Nested Subqueries: Hard to read, scan, and maintain
SELECT d.department_name, ds.headcount
FROM (
    SELECT dept_id, COUNT(*) AS headcount
    FROM (
        SELECT name, salary, dept_id 
        FROM employees 
        WHERE salary > 70000
    ) AS high_earners
    GROUP BY dept_id
) ds
JOIN departments d ON ds.dept_id = d.id;

A Common Table Expression (CTE) solves this.

By using the WITH clause, you declare named, temporary virtual tables at the start of your script and query them sequentially:

sql — cte_refactored.sql 
-- ✅ Clean, modular, and self-documenting
WITH high_earners AS (
    SELECT name, salary, dept_id
    FROM employees
    WHERE salary > 70000
),
dept_summary AS (
    SELECT dept_id, COUNT(*) AS headcount
    FROM high_earners
    GROUP BY dept_id
)
SELECT d.department_name, ds.headcount
FROM dept_summary ds
JOIN departments d ON ds.dept_id = d.id
ORDER BY ds.headcount DESC;

2.1. Recursive CTEs — Tree Traversal

Standard SQL joins cannot query hierarchical structures (like company org charts or nested website categories) where the depth is unknown.

Recursive CTEs loop through rows until no more connections are found.

sql — recursive_org_chart.sql 
WITH RECURSIVE org_chart AS (
    -- 1. Anchor Member: Find the top-level bosses (manager_id is NULL)
    SELECT id, name, manager_id, 1 AS level
    FROM employees
    WHERE manager_id IS NULL
    
    UNION ALL
    
    -- 2. Recursive Member: Join the CTE back to find direct reports
    SELECT e.id, e.name, e.manager_id, o.level + 1
    FROM employees e
    INNER JOIN org_chart o ON e.manager_id = o.id
)
SELECT * FROM org_chart ORDER BY level, name;

To use window functions, we use the OVER clause.

It defines the "window" or partition of data the function calculates across.

Let's break down the syntax step-by-step:

Ranking Functions: ROW_NUMBER vs. RANK vs. DENSE_RANK

Suppose three employees in the IT department earn the exact same salary ($80,000).

How do different ranking functions rank them?

  • ROW_NUMBER() : Assigns a unique consecutive number to every row (1, 2, 3) ignoring ties.
  • RANK() : Assigns the same rank to ties, but skips the next rank numbers (1, 1, 1, 4).
  • DENSE_RANK() : Assigns the same rank to ties without skipping numbers (1, 1, 1, 2).
sql — window_rankings.sql 
SELECT name, department, salary,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS row_num,
    RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
    DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dense_rnk
FROM employees;

Time-Series Row Comparisons: LEAD and LAG

LEAD() fetches a value from a subsequent row, and LAG() fetches a value from a preceding row.

They allow you to compare rows sequentially without expensive self-joins (perfect for Month-over-Month changes).

sql — lead_lag.sql 
SELECT month, revenue,
    LAG(revenue, 1) OVER (ORDER BY month) AS prev_month_revenue,
    revenue - LAG(revenue, 1) OVER (ORDER BY month) AS mom_change
FROM monthly_sales;

5. EXISTS vs. IN — Performance & Null Behaviors

To check if a value exists in another set, we use IN or EXISTS .

But they act differently under the hood:

  • IN : The database retrieves the entire subquery result set, caches it in memory, and checks if the outer value exists in that set.
  • EXISTS : The database uses a semi-join . It stops searching the moment it finds the first matching record in the subquery. For large subqueries, EXISTS is significantly faster!
sql — exists_vs_in.sql 
-- Use IN for small, static lists (e.g. IN (1, 2, 3))
SELECT name FROM employees
WHERE dept_id IN (
    SELECT id FROM departments WHERE location = 'Mumbai'
);

-- Use EXISTS for large subqueries (Faster execution)
SELECT e.name FROM employees e
WHERE EXISTS (
    SELECT 1 FROM departments d
    WHERE d.id = e.dept_id AND d.location = 'Mumbai'
);

6. Running Aggregates — Dynamic Windows

By ordering inside the OVER clause, we can compute cumulative and rolling metrics over time:

sql — running_aggregates.sql 
SELECT month, revenue,
    SUM(revenue) OVER (ORDER BY month) AS running_total,
    AVG(revenue) OVER (
        ORDER BY month
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

8. Database Triggers — Event-Driven Automation

A Trigger automatically executes a procedure in response to INSERT , UPDATE , or DELETE events on a specific table.

This is perfect for security auditing and maintaining history logs:

sql — triggers.sql 
-- 1. Audit log table
CREATE TABLE salary_audit_log (
    emp_id INT,
    old_salary INT,
    new_salary INT,
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. Trigger Function (PostgreSQL PL/pgSQL syntax)
CREATE OR REPLACE FUNCTION log_salary_change()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit_log(emp_id, old_salary, new_salary)
        VALUES(OLD.id, OLD.salary, NEW.salary);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 3. Bind the trigger to run BEFORE the update executes on each row
CREATE TRIGGER trg_salary_update
BEFORE UPDATE ON employees
FOR EACH ROW
EXECUTE FUNCTION log_salary_change();

Cursors — Row-by-Row Iteration

While standard SQL works on sets of rows simultaneously, a Cursor is a pointer that allows you to iterate through query results row-by-row, running loops and conditional operations in a procedural container.

sql — cursors.sql 
CREATE OR REPLACE FUNCTION distribute_bonuses() RETURNS VOID AS $$
DECLARE
    emp_record RECORD;
    emp_cursor CURSOR FOR SELECT id, salary FROM employees WHERE perf_score >= 9;
BEGIN
    OPEN emp_cursor;
    LOOP
        FETCH NEXT FROM emp_cursor INTO emp_record;
        EXIT WHEN NOT FOUND;
        
        UPDATE employees 
        SET salary = salary + (emp_record.salary * 0.10) 
        WHERE id = emp_record.id;
    END LOOP;
    CLOSE emp_cursor;
END;
$$ LANGUAGE plpgsql;

10. Transactions & ACID Properties

Transactions bundle multiple SQL writes into a single, atomic block.

Either all operations succeed, or none do.

This preserves database integrity in the event of hardware failures or network cuts.

  • Atomicity: All statements in a transaction succeed, or everything is rolled back (All-or-Nothing).
  • Consistency: The database transitions cleanly according to rules (e.g. constraints, unique keys).
  • Isolation: Concurrent transactions run independently and do not read uncommitted states.
  • Durability: Once committed, updates are permanently written to disk and survive system crashes.
sql — transactions.sql 
BEGIN;
    UPDATE accounts SET balance = balance - 1000 WHERE id = 1;  -- Debit
    UPDATE accounts SET balance = balance + 1000 WHERE id = 2;  -- Credit
COMMIT;   -- Persists changes on disk

-- If an operation fails, run ROLLBACK to revert to initial state:
BEGIN;
    DELETE FROM orders WHERE status = 'cancelled';
ROLLBACK;  -- Reverts the deletes

11. Database Locks — Shared vs. Exclusive

-- 1. Shared Lock (FOR SHARE): Allows others to read, blocks write updates
SELECT balance FROM accounts WHERE id = 1 FOR SHARE;

-- 2. Exclusive Lock (FOR UPDATE): Blocks others from both reading and writing
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;

15. pgvector — Modern Vector Search & Similarity

Keyword search using operators like LIKE '%python%' has a major limitation: it only returns exact character matches.

If a user searches for "machine learning", keyword queries fail to match documents containing "ML", "neural networks", or "deep learning" because the terms are textually different, despite being semantically similar.

Modern LLM applications (like Retrieval-Augmented Generation or RAG) convert text blocks into high-dimensional numerical lists called vector embeddings .

The pgvector extension allows PostgreSQL to store, index, and query vectors directly alongside your relational tables:

In RAG architectures, we embed a user's natural language question, run a vector similarity query in PostgreSQL to retrieve the most relevant background documents, and pass that retrieved text as context to LLMs like Claude or GPT.
sql — pgvector_search.sql 
-- 1. Enable pgvector extension
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Create table storing text alongside 1536-dimensional embeddings (OpenAI standard)
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT,
    embedding VECTOR(1536)
);

-- 3. Perform Cosine Similarity vector search to find top 3 matching documents
SELECT content, 1 - (embedding <=> '[0.012, -0.004, ..., 0.89]') AS cosine_similarity
FROM documents
ORDER BY embedding <=> '[0.012, -0.004, ..., 0.89]' ASC
LIMIT 3;

-- Distance Operators:
-- <=> Cosine Distance (used for textual semantic similarity)
-- <-> L2 Euclidean Distance (used for physical distance/coordinate metrics)
-- <#> Negative Inner Product
