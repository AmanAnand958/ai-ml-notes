🧠 Theory & Concepts

1. The Message Structure — System, User, Assistant

Ek LLM ko baat karne ka ek specific format hota hai. Ye ek chat window nahi hai — ye ek structured message array hai. Teen roles hain:

Role Purpose Example
system Sets the AI's persona, rules, and constraints. Processed first, highest priority. "You are a Python expert who only answers in code."
user The human's actual question or request. "Write a function to reverse a linked list."
assistant Previous AI responses — used to build conversation history (few-shot examples too). Prior answers in the conversation.

2. Zero-shot vs Few-shot vs Many-shot

Zero-shot: No examples given — model relies entirely on its training. Works best for clear, standard tasks. "Classify this review as positive or negative: 'The movie was fantastic!'"

Few-shot: 2–5 examples in the prompt that demonstrate the format/task. Dramatically improves consistency for novel or structured outputs. The examples act as in-context training .

Many-shot: 10–100+ examples. Useful for very specific output formats. Limited by context window.

3. Chain-of-Thought (CoT) Prompting

CoT ek revolutionary technique hai jisse LLMs ke reasoning ability dramatically improve hoti hai. Sirf "Let's think step by step" add karne se complex reasoning tasks mein 30–50% accuracy improve hoti hai.

Why CoT works — probability decomposition: $$P(\text{correct answer}) = \prod_{i=1}^{n} P(\text{step}_i \mid \text{steps}_{1..i-1})$$ Each intermediate reasoning step conditions the next, reducing the probability of errors cascading from a single wrong jump.

4. ReAct Prompting (Reason + Act)

ReAct is the foundation of all modern AI agents. The model interleaves Thought (reasoning), Action (tool use), and Observation (tool result) in a loop until the task is complete.

graph LR A["Question"] --> B["Thought: Reason about what to do"] B --> C["Action: Call a tool or API"] C --> D["Observation: Get tool result"] D --> E["Task done?"] E -->|No| B E -->|Yes| F["Final Answer"] style A fill:#1c2030,stroke:#38bdf8,color:#dde2f0 style F fill:#1c2030,stroke:#4fd1a5,color:#dde2f0

5. Sampling Parameters — Controlling Randomness

Parameter Range Effect When to Use
temperature 0.0 – 2.0 Scales logit distribution. 0 = deterministic (greedy), 1 = normal, >1 = chaotic 0 for factual/code, 0.7 for balanced, 1.2+ for creative writing
top_p 0.0 – 1.0 Nucleus sampling: only consider tokens whose cumulative probability ≤ top_p 0.9 default. Use with temperature, not instead of it
top_k 1 – ∞ Only sample from the top-k tokens at each step 40–100 for diversity, 1 for greedy
max_tokens 1 – model max Hard cap on output length Set low for structured outputs, high for long-form
Temperature scaling on logits before softmax: $$P(w_i) = \frac{\exp(z_i / T)}{\sum_{j} \exp(z_j / T)}$$ T → 0: distribution collapses to argmax (greedy). T → ∞: uniform distribution (pure random).

Prompt injection tab hota hai jab malicious user input apne andar hidden instructions daal deta hai jo model ke original instructions ko override karne ki koshish karta hai. Ye LLM security ka #1 threat hai.

7. Advanced Prompt Patterns

  • Persona Pattern: "Act as a senior Google SWE reviewing this code."
  • Output Format Specification: "Respond ONLY as valid JSON with keys: {name, score, reason}."
  • Negative Constraints: "Do not use bullet points. Do not mention competitors."
  • Role Reversal: "Ask me clarifying questions before answering."
  • Self-Consistency: Generate multiple answers at temperature=0.7, then vote on majority.
  • Tree of Thought (ToT): Branch multiple reasoning paths and evaluate which path is best.

# faiss_ivfflat_vs_flatl2_performance_benc.py — Solution
# Complete solution for: FAISS IVFFlat vs FlatL2 Performance Benchmark

import numpy as np

class RandomForestClassifierScratch:
    """Random Forest Classifier with Bootstrap Sampling and Feature Subsampling."""
    def __init__(self, n_estimators=10, max_depth=5, max_features='sqrt'):
        self.n_estimators = n_estimators
        self.max_depth = max_depth
        self.max_features = max_features
        self.trees = []

    def fit(self, X, y):
        X, y = np.asarray(X), np.asarray(y)
        n_samples, n_features = X.shape
        from sklearn.tree import DecisionTreeClassifier
        self.trees = []
        
        for _ in range(self.n_estimators):
            # Bootstrap sampling
            indices = np.random.choice(n_samples, size=n_samples, replace=True)
            X_boot, y_boot = X[indices], y[indices]
            
            # Select sub-features
            tree = DecisionTreeClassifier(max_depth=self.max_depth, max_features=self.max_features)
            tree.fit(X_boot, y_boot)
            self.trees.append(tree)
        return self

    def predict(self, X):
        predictions = np.array([tree.predict(X) for tree in self.trees])
        # Majority voting across trees
        from scipy.stats import mode
        m, _ = mode(predictions, axis=0)
        return m.ravel()

# Test
from sklearn.datasets import make_classification
X, y = make_classification(n_samples=200, n_features=10, random_state=42)
rf = RandomForestClassifierScratch(n_estimators=15, max_depth=4)
rf.fit(X, y)
acc = (rf.predict(X) == y).mean()
print(f"Random Forest Training Accuracy: {acc:.4f}")

🧪 Quiz

Q1 OF 5
Why must FAISS vectors be float32 , not float64 (the numpy default)?
A float64 causes FAISS to produce incorrect similarity scores
B It's just a legacy limitation with no practical consequence
C FAISS uses SIMD (AVX2) CPU instructions that are optimized for 32-bit floats — it raises a TypeError for float64 and float32 halves memory usage, enabling more vectors per CPU cache line
D float64 is not supported by Python
✅ Correct! FAISS uses vectorized SIMD instructions (SSE/AVX) optimized for float32. This enables massive parallelism at the CPU level. Always call .astype('float32') on your numpy arrays before FAISS operations.
❌ FAISS requires float32 for two reasons: (1) its SIMD (AVX2) optimisations are written for 32-bit floats, (2) float32 uses half the memory of float64, allowing 2x more vectors per cache line.
Q2 OF 5
For two normalised unit vectors, what is the relationship between L2 distance and cosine similarity?
A They have no mathematical relationship
B $\|a - b\|^2 = 2(1 - \cos\theta)$, so maximising cosine similarity is equivalent to minimising L2 distance for unit vectors
C L2 distance equals cosine similarity numerically
D L2 distance only works for integer vectors
✅ Perfect. $\|a-b\|^2 = \|a\|^2 + \|b\|^2 - 2a\cdot b = 1 + 1 - 2\cos\theta = 2(1-\cos\theta)$. So for normalised vectors, ranking by L2 distance gives the same order as ranking by cosine similarity. This is why we normalise before using IndexFlatIP.
❌ For unit vectors: $\|a-b\|^2 = 2(1-\cos\theta)$. Minimising L2 = maximising cosine similarity when both vectors are normalised. This is why normalising before FAISS IndexFlatIP gives cosine similarity results.
Q3 OF 5
What does the nprobe parameter in FAISS IndexIVFFlat control?
A The number of results to return
B The number of dimensions to use
C The number of Voronoi cells (clusters) to search during query — higher nprobe = higher recall but slower query time
D The number of training iterations for the k-means clustering step
✅ Correct! IVFFlat partitions the vector space into nlist Voronoi cells during indexing. At query time, it only searches nprobe cells (not all nlist). nprobe=1 = fastest, lowest recall. nprobe=nlist = same as exact search but slower to build.
❌ nprobe controls how many Voronoi cells (clusters) to search during a query. IVFFlat partitions the space into nlist clusters. At query time, only nprobe nearest clusters are searched. Higher nprobe → better recall, slower speed.
Q4 OF 5
You have 50 million vectors and need real-time queries with <10ms latency. Which FAISS index should you use?
A IndexFlatL2 — always use exact search for accuracy
B IndexIVFFlat with nlist=100
C IndexHNSWFlat or IndexIVFPQ — hierarchical NSW or product-quantized IVF for sub-linear query time and memory efficiency at hundreds of millions of vectors
D ChromaDB — it handles all scale automatically
✅ Correct! At 50M vectors: FlatL2 would take ~5 seconds per query. IVFFlat is better but still memory-heavy. HNSW provides sub-10ms queries at high recall. IVF+PQ compresses vectors to save RAM. For production at this scale, also consider Pinecone, Weaviate, or Qdrant.
❌ At 50M vectors, exact search is too slow. HNSW (Hierarchical Navigable Small World) provides ~logarithmic query time with ~98% recall. IVF+PQ adds product quantisation to reduce memory. These are the production-grade choices at this scale.
Q5 OF 5
What does normalize_embeddings=True do in sentence-transformers' encode() , and when should you use it?
A It normalises the input text to lowercase before encoding
B It removes outlier dimensions from the embedding
C It L2-normalises each vector to unit length, so that dot product equals cosine similarity — use it whenever you want to measure semantic similarity rather than magnitude
D It makes all embeddings have values between 0 and 1 using min-max scaling
✅ Exactly. L2-normalisation divides each vector by its L2 norm, making $\|v\| = 1$. After normalisation, cosine similarity = dot product (no division needed). Always normalise when using FAISS IndexFlatIP or any cosine similarity computation.
❌ normalize_embeddings=True applies L2-normalisation: each vector is divided by its magnitude so $\|v\|=1$. For unit vectors, dot product = cosine similarity. Always use this when you want similarity to reflect semantic closeness, not vector magnitude.

PYTHON — RECURSIVE TEXT SPLITTER 
from typing import List, Dict

def compute_rrf_hybrid_search(
    bm25_ranks: Dict[str, int], 
    vector_ranks: Dict[str, int], 
    k: int = 60
) -> List[Dict]:
    """
    Reciprocal Rank Fusion (RRF) for Combining Sparse BM25 and Dense Vector Search.
    Formula: RRF_Score(d) = 1/(k + rank_bm25(d)) + 1/(k + rank_vec(d))
    """
    all_doc_ids = set(bm25_ranks.keys()).union(set(vector_ranks.keys()))
    rrf_scores = {}
    
    for doc_id in all_doc_ids:
        score = 0.0
        if doc_id in bm25_ranks:
            score += 1.0 / (k + bm25_ranks[doc_id])
        if doc_id in vector_ranks:
            score += 1.0 / (k + vector_ranks[doc_id])
        rrf_scores[doc_id] = score
        
    ranked = sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True)
    return [{"doc_id": doc, "rrf_score": round(score, 5)} for doc, score in ranked]

# Example execution
bm25_results = {"doc_101": 1, "doc_102": 2, "doc_103": 3}
vector_results = {"doc_103": 1, "doc_101": 2, "doc_104": 3}
fused = compute_rrf_hybrid_search(bm25_results, vector_results, k=60)
print("Hybrid RRF Ranks:", fused)

3. Hybrid Search — BM25 + Vector Similarity

BM25 is the gold standard keyword search (used by Elasticsearch, Solr). It catches exact keyword matches that vector search misses. Vector search catches semantic matches that BM25 misses. Combined = best of both worlds.

BM25 score for query term t in document d: $$\text{BM25}(t,d) = \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1 + 1)}{f(t,d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}$$ Where f(t,d) = term frequency, |d| = document length, avgdl = avg doc length, k₁=1.5, b=0.75 are tuning params.
PYTHON — HYBRID SEARCH WITH RECIPROCAL RANK FUSION 
from typing import List, Dict

class CrossEncoderReranker:
    """
    Cross-Encoder Re-ranker: Performs joint full self-attention over [CLS] Query [SEP] Document [SEP]
    to output an uncompressed relevance probability score.
    """
    def __init__(self, model_name: str = "cross-encoder/ms-marco-MiniLM-L-6-v2"):
        self.model_name = model_name

    def predict_relevance(self, query: str, candidate_docs: List[str]) -> List[Dict]:
        # Simulated Cross-Encoder scoring (in production: cross_encoder.predict([[query, d] for d in candidate_docs]))
        results = []
        for idx, doc in enumerate(candidate_docs):
            query_terms = set(query.lower().split())
            doc_terms = set(doc.lower().split())
            overlap = len(query_terms.intersection(doc_terms)) / max(1, len(query_terms))
            score = 1.0 / (1.0 + np.exp(- (2.5 * overlap - 0.5))) # Sigmoid calibrated score
            results.append({"doc_id": f"doc_{idx+1}", "text": doc, "cross_encoder_score": round(float(score), 4)})
            
        ranked = sorted(results, key=lambda x: x["cross_encoder_score"], reverse=True)
        return ranked

A user asks "What did CEO say in Q3 earnings call?" but your vector search returns "Q2 results were strong" (wrong quarter). BM25 returns the correct Q3 document. This is an example of which vector search failure mode?
A Context window overflow
B Vocabulary mismatch — "Q3" and "Q2" have similar embeddings (both are earnings-related) but BM25 correctly distinguishes them via exact keyword matching
C Hallucination by the LLM
D Insufficient chunk overlap
✅ Exactly. Vector search captures semantic similarity — Q2 and Q3 earnings reports are semantically similar (same domain, same structure). BM25 distinguishes them via exact term matching. This is the primary motivation for hybrid search.
❌ This is a vocabulary mismatch failure. "Q3" and "Q2" are semantically similar (both quarterly earnings) but factually different. BM25 correctly matches exact tokens like "Q3". Hybrid search is the solution.
Q2 OF 5
In Reciprocal Rank Fusion (RRF), why is the constant k=60 used in the formula $\frac{1}{k + \text{rank}}$?
A 60 is the maximum number of results any retrieval system can return
B k prevents very highly-ranked documents from dominating the score — without k, rank=1 gives score=1.0 while rank=2 gives 0.5 (50% drop). k=60 makes the ranking smoother and less sensitive to small rank differences
C k=60 was chosen to match the default FAISS nlist parameter
D It's an arbitrary constant with no theoretical justification
✅ Correct. Without k, 1/1=1.0 vs 1/2=0.5 — a rank-1 document gets 2x the score of rank-2. With k=60: 1/61 vs 1/62 — nearly equal. This smoothing was empirically shown to work well at k=60 in the original RRF paper (Cormack et al., 2009).
❌ k prevents top-1 documents from completely dominating. With k=60, rank differences of a few positions have much smaller impact on the final score, making the fusion more robust to rank noise.
Q3 OF 5
What is the key difference between a bi-encoder and a cross-encoder for retrieval?
A Bi-encoder encodes query and document independently (fast, scalable for large corpora). Cross-encoder processes them jointly, allowing attention between them (accurate but too slow for large-scale retrieval)
B Bi-encoder is used for short texts, cross-encoder for long documents
C They are the same architecture but bi-encoder uses 2 GPUs
D Cross-encoder cannot be used with FAISS
✅ Perfect. Bi-encoder: query → vector, doc → vector (pre-computed), compare at search time. O(1) per query. Cross-encoder: feed [query, doc] together, output relevance score. O(N) per query. Solution: bi-encoder for retrieval (fast), cross-encoder for reranking (accurate on small set).
❌ Bi-encoder = independent encoding (fast, scalable). Cross-encoder = joint processing with attention between query and document (accurate, but can't pre-compute — must process every query-document pair at query time, making it O(N)).

Your RAG system has Faithfulness=0.95 but Context_Recall=0.40. What does this tell you?

Q5 OF 5
Why should chunk_overlap be set to 10–15% of chunk_size in RecursiveCharacterTextSplitter?
A To reduce storage costs by duplicating some text
B To preserve context at chunk boundaries — an answer that spans two chunks is more likely to be retrievable because both chunks contain the bridge text
C To improve BM25 ranking scores by increasing term frequency
D Overlap is optional and has no practical benefit
✅ Exactly. Without overlap, a sentence that starts in chunk N and ends in chunk N+1 would never be fully retrievable. Overlap ensures that boundary sentences appear in both chunks, so they can be retrieved by either. 10–15% overlap is the empirical sweet spot.
❌ Overlap handles the chunk boundary problem. Without it, sentences that cross chunk boundaries are split and neither chunk contains the complete thought. Overlap ensures boundary content appears in adjacent chunks, making it retrievable.

2. OpenAI Function Calling — Tool Definition

Function calling allows developers to describe application functions to LLMs, which return structured arguments for executing local actions.

PYTHON — OPENAI FUNCTION CALLING 
import json, openai, math

client = openai.OpenAI()

# --- Define tools as JSON schemas ---
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "Evaluate a mathematical expression. Use this for any arithmetic.",
            "parameters": {
                "type": "object",
                "properties": {
                    "expression": {
                        "type": "string",
                        "description": "Python math expression, e.g. '2 ** 10' or 'math.sqrt(144)'"
                    }
                },
                "required": ["expression"]
            }
        }
    }
]

# --- Tool execution function ---
def execute_tool(name: str, args: dict) -> str:
    if name == "calculate":
        try:
            result = eval(args["expression"], {"math": math, "__builtins__": {}})
            return str(result)
        except Exception as e:
            return f"Error: {e}"
    return "Tool not found"

# --- Agent loop ---
messages = [{"role": "user", "content": "What is 17 raised to the power of 5, divided by 1024?"}]

while True:
    response = client.chat.completions.create(
        model="gpt-4o-mini", messages=messages, tools=TOOLS, tool_choice="auto"
    )
    msg = response.choices[0].message
    messages.append(msg)  # add assistant message to history

    if msg.tool_calls:
        # Model wants to call a tool
        for tc in msg.tool_calls:
            args   = json.loads(tc.function.arguments)
            result = execute_tool(tc.function.name, args)
            print(f"Tool: {tc.function.name}({args}) → {result}")
            # Add tool result back to conversation
            messages.append({
                "role":         "tool",
                "tool_call_id": tc.id,
                "content":      result
            })
    else:
        # Model finished — no more tool calls
        print(f"\nFinal Answer: {msg.content}")
        break

import math, datetime, requests

# Define tools using @tool decorator
# The docstring becomes the tool description — make it clear and specific

@tool
def calculator(expression: str) -> str:
    """Evaluate a mathematical expression. Input: valid Python math expression.\n    Examples: '210', 'math.sqrt(144)', '(15 * 3) / (2 + 1)'"""
    try:
        return str(eval(expression, {"math": math, "__builtins__": {}}))
    except Exception as e:
        return f"Error: {e}"

@tool
def get_current_date() -> str:
    """Get today's current date and time. Use when the user asks about the current date."""
    return datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S")

@tool
def web_search(query: str) -> str:
    """Lightweight web search using DuckDuckGo Instant Answer API (demo).\n    Returns a short text snippet for the query."""
    try:
        resp = requests.get("https://api.duckduckgo.com", params={"q": query, "format": "json"}, timeout=5)
        data = resp.json()
        return data.get("AbstractText") or data.get("Heading") or "No results"
    except Exception as e:
        return f"Error: {e}"

@tool
def python_repl(code: str) -> str:
    """Execute a tiny Python snippet in a restricted locals dict and\n    return a textual result. THIS IS FOR DEMO ONLY — not safe for untrusted code."""
    try:
        local = {}
        exec(code, {"__builtins__": {}}, local)
        return str(local.get("result", "Executed"))
    except Exception as e:
        return f"Error: {e}"

Dividing a complex task among specialized agents (e.g., researcher, writer, editor) reduces prompt complexity and improves reliability.
What is human-in-the-loop (HITL) inside agentic systems?
A checkpoint where the agent pauses and waits for user approval or feedback before executing a critical tool (like sending an email or running a transaction).
⚠️ Gotcha: CUDA Out-of-Memory (OOM) Overhead

PyTorch allocates memory in cached chunks. Use `torch.cuda.empty_cache()` and gradient accumulation when batch sizes hit limits.
